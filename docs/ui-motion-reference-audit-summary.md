# Lucian UX/UI Prompt 400개 실사 감사 요약

2026-10-19 기준 [Lucian UX/UI Prompt](https://lucianlabs.dev/uxui-prompt/)의 400개 컴포넌트·애니메이션을 네 구간으로 나누어 확인했다. 네 감사 문서는 모두 구간별 이름·분류 100개와 실제 렌더링 100개를 기록한다. 따라서 합계는 **카탈로그 400개 / 렌더 미리보기 관찰 400개**다. 다만 카드가 화면에 나타난 것을 관찰한 범위이며, 각 애니메이션의 모든 시간대·상태·화면 크기를 확인했다는 뜻은 아니다.

## 구간별 기록과 상호작용 범위

| 구간 | 감사 기록 | 렌더 검토 | 실제 조작 기록 |
| --- | --- | ---: | --- |
| [001–100](ui-motion-reference-audit-001-100.md) | 영어 문서. 겹치는 갤러리 화면에서 ID와 미리보기 확인 | 100/100 | 21개 시도, 20개에서 화면 변화 확인, ID 025는 실패로 기록 |
| [101–200](ui-motion-reference-audit-101-200.md) | 한국어 문서. 4개 분류, 36개 캡처 | 100/100 | 40개 조작 행, 상태 변화 34개, 성공으로 세지 않은 시도 6개 |
| [201–300](ui-motion-reference-audit-201-300.md) | 한국어 문서. 분류 필터와 전체 스크롤, 결과가 불명확한 조작은 따로 표기 | 100/100 | 27개 카드 조작. 그중 결과가 모호하거나 확인되지 않은 항목이 있어 성공 수를 합산하지 않음 |
| [301–400](ui-motion-reference-audit-301-400.md) | 영어 도입부·한국어 표. 1440×1000 중첩 스크린샷 | 100/100 | 31개 카드에서 35회 조작, 30회 상태 변화 확인, 5회는 해결 또는 완료되지 않음 |

각 문서가 ‘시도’, ‘카드 수’, ‘상태 변화’를 다르게 집계한다. 단순 합산하면 **119개 카드에 123회 조작**을 했고, 이 중 세 구간에서 명시적으로 확인한 변화는 84회(20+34+30)다. 201–300은 결과를 확정하지 않은 조작을 별도로 서술하므로 여기에 성공 수를 더하지 않았다. 이 숫자는 400개 전체의 완전한 상호작용 테스트를 뜻하지 않는다. 나머지는 렌더만 관찰했으며, 별도 문서가 다루지 않은 키보드·스크린리더·감소 모션·브라우저 간 동작·소스 라이선스 검토도 포함하지 않는다.

**관찰 증거의 강도는 구간마다 다르다.** 001–100 문서는 모든 행의 렌더 관찰을 “Card preview and its identifying UI were visible”로만 적어 어떤 그림·상태가 실제로 보였는지 ID별 세부 증거가 약하다. 이 구간의 100/100은 스크린샷에서 해당 카드와 식별 UI를 봤다는 기록이지, 시각 결과를 구체적으로 평가한 기록은 아니다. 101–200은 캡처 방법과 상태 비교를 보강했고, 201–300은 불확실한 결과를 명시적으로 남겼다. 301–400은 카드마다 실제 화면의 요소를 구체적으로 기술했다. 따라서 전체 렌더 수는 400으로 보고하되, 이를 같은 깊이의 리뷰로 과장하지 않는다.

## 우리 갤러리에서 바로 고쳐야 할 다섯 가지

1. **같은 데모 틀을 반복하는 구성.** 여러 컴포넌트가 같은 제목·설명·조작 행과 거의 같은 무대 안에 들어가면, 데모의 목적이 사라진다. 첫 화면부터 각 카드의 주인공과 정보 위계를 다르게 설계해야 한다.
2. **모든 모션을 같은 진입 효과로 처리.** 단발로 나타났다 멈추는 애니메이션만으로는 상태 변화나 진행을 설명하지 못한다. 조작 결과와 연결된 지속 상태, 되돌리기, 취소, 완료 동작을 각각 설계해야 한다.
3. **작은 카드 안에서 읽히지 않는 라벨.** 미세한 값·범례·보조 문구를 축소해 넣기보다, 카드 크기에서 읽을 핵심 정보만 남기고 정밀 제어는 넓은 상세 보기로 옮긴다.
4. **완성도가 낮은 임시 무대와 플레이스홀더.** 빈 검정 패널이나 장식용 모양은 제품 맥락을 만들지 못한다. 이미지·데이터·작업 대상·피드백을 포함한 실제 화면으로 각 데모를 완성해야 한다.
5. **모든 시각 상태를 확인하지 않은 채 완료 처리.** 렌더 확인과 조작 확인은 다르며, 조작 시도와 성공한 변화도 다르다. 상태별 전후를 확인하고 실패·미확인 결과를 표시해야 한다. 네 감사 기록에서도 일부 필터, 입력, 자동 검색, 비동기 상태는 확인되지 않았다.

## 옮겨 쓸 수 있는 구체적 패턴

- **조작값과 결과를 한 장면에서 연결한다.** 301은 포맷·품질·비교선을 사진과 용량 절감에 묶고, 316은 강성·감쇠 조작과 스프링 반응을 같은 패널에 둔다. 우리 슬라이더와 선택 컨트롤도 실제 산출물을 바꾸도록 만든다.
- **모션이 공간·관계를 설명하게 한다.** 318의 경로는 도시 사이 이동을, 344의 핀은 지도 위 위치를, 391의 곡선은 부서 간 연결을 보여 준다. 장식적 움직임보다 기능 의미를 읽히게 한다.
- **깊이와 색을 목적에 따라 쓴다.** 202의 입체 데이터 블록, 337의 지도 채색, 349의 사진 전환은 차트·지리·이미지라는 주제를 바로 드러낸다. 공유 프레임은 일관되게 유지하되, 각 컴포넌트가 필요로 하는 재질·색·이미지는 다르게 연출한다.
- **복잡한 데이터는 작은 화면에서도 구조를 보이게 한다.** 326의 와플 차트와 범례, 398의 회귀선·잔차 토글, 400의 동기화 커서는 데이터 간 관계를 시각화한다. 우리 차트는 큰 데이터 흔적을 먼저 보여 주고 설명과 제어를 가까이 둔다.
- **입력과 피드백을 짝지어 보여 준다.** 303의 글꼴 선택은 제목·본문 견본을, 361의 이동 버튼은 현재 슬라이드를, 396의 재가리기는 스포일러 상태를 바꾼다. 클릭 색상만 바뀌는 수준을 넘어서 결과물의 정보나 구성이 변해야 한다.

이 패턴들은 Lucian의 어두운 그라데이션 카드 틀을 그대로 가져오라는 뜻이 아니다. 우리 갤러리의 시각 언어는 일관되게 유지하면서, 개별 데모는 그 기능에 맞는 소재와 구도, 깊이, 움직임으로 다시 설계한다. 감사 중 참고 화면·타사 코드·이미지 자산은 저장소 구현에 복사하지 않았다.
